# Decisions

What's been settled for gnoto, and what was set aside, as of 2026-11-09. Don't reopen these
unless Daniel asks or testing proves one unworkable. If one changes, update this file and
[design.md](design.md) together.

## Daniel's decisions

| Decision | Why | Set aside |
| --- | --- | --- |
| The name is `gnoto`, for the repo and the command | From gnotobiotic: everything present is known. Free on the registries checked | `axenic`, `chemostat`, `biomrun`, `petri`, `agar`, `scoby` |
| New repo `cmmr/gnoto`, with `cmmr/nextflow` left as a reference | A clean, public history | Renaming the old repo |
| Nothing is in production, so overhaul freely. Daniel tears everything down and rolls out as an external user would | The rollout doubles as the final test | Compatibility, cutover, honoring old runs and published results |
| Install from a release tarball | No git needed to install, a fixed URL, and a checksum | `git clone`, a `curl \| bash` installer, Bioconda |
| `gnoto upgrade` fetches the release into `versions/` and rewrites `<data_dir>/current`. Every command runs from the current release's copy, and the only install-directory files gnoto uses are the launcher, which is never upgraded, and `config.yaml`. `core.data_dir` defaults to `<install directory>/data` | Nothing is overwritten, so running commands and jobs keep their code, no stale files linger, and going back is a pointer move | Replacing the installed code in place |
| Settings and secrets go in one gitignored `config.yaml` | One friendly file | `.env`, a separate secrets file |
| `config.yaml` is optional and minimal, so opening it shows what's in effect. Without it, gnoto runs with every setting at its default: data in `<install>/data`, jobs run locally, and Apptainer and Slurm found on `PATH`. When Apptainer isn't on `PATH`, `gnoto init --apptainer=<path>` writes a `config.yaml` holding only an `apptainer` section that says where it is, runs nothing in the image, and refuses if `config.yaml` exists. Later container engines get their own option in place of `--apptainer`. `gnoto config` prints each section and what it's for, one per line. `gnoto config <section>` asks for that section's settings, and `--on` or `--off` sets its `enabled`; either way a section `config.yaml` lacks is added whole, with the answers or with every suggestion, and only that section. `lib/config/<section>.sh` declares each section's settings, types, defaults and questions, and how to find suggestions, such as from `sinfo`. A new `config.yaml` is mode 660 in the user's own group, and answers are written into their lines, keeping comments, mode and group (Daniel, 2026-11-06) | Starting should take nothing but Apptainer, and `init` is the one step for a machine where it isn't on `PATH`, since nothing else can run without it. A file holding only what a site chose is easy to read. Recording Slurm's directory and `SLURM_CONF` keeps gnoto working from shells that haven't loaded a Slurm module | Shipping `config.example.yaml` for people to copy and edit. Asking on the terminal on the first run. A `gnoto install` that must run first. Writing every setting into `config.yaml`, from a `config_defaults.yaml` or an `auto_config.sh` |
| Every section of `config.yaml` but `core` starts with `enabled`, so it can be set up but not used, and `gnoto config <section> --on` or `--off` toggles it. A section is on only when `enabled` is `true`, except `apptainer`, which is on unless it says `false`, and can't be turned off while it's the only container engine. Each backend has its own section, `slurm:` and `apptainer:` so far, and its `enabled` picks it: jobs go to Slurm when `slurm.enabled` is `true` and run locally otherwise (Daniel, 2026-11-06) | One switch per section says what's active, so no setting has to name the backend | `core.scheduler` and `core.container_engine`. `core.executor`, with Slurm's and Apptainer's settings under `core:` |
| Add `yq`, and use YAML wherever it's easy. Only `run_state.json` and `progress.json` stay JSON | Consistency | A hand-written parser for a YAML subset, keeping config files as JSON |
| The filled-in job is `job.yaml`, and the full record is `record.yaml` | `job.yaml` and `job.json` were too alike | `job.json` |
| Users install only Apptainer: a `gnoto` image holds the tools, and a host helper runs Slurm, Apptainer and systemd commands | Daniel wanted as little as possible on the host | Tools on the host, binding Slurm files into the image, nested containers |
| Drop the `_01` numbering, in favor of `pipelines/<name>/` and release tags | Reruns pin the commit, so in-place edits are safe | Numbered pipeline files, separate repos per pipeline |
| No `gnoto new --from` | `cp job.yaml new.yaml` does the same thing | A dedicated command |
| CLI jobs get a Wrike task when Wrike is configured | They get the same status updates and expiry as form requests | CLI jobs staying out of Wrike |
| `run` and `start` create a CLI job's Wrike task directly in the `Running` status, so it's never waiting and `gnoto wrike` passes it by | Wrike's task creation accepts a status, so no extra field is needed | A `Source: cli` custom field that `gnoto wrike` checks |
| CLI jobs run as the calling user | Slurm accounting and file ownership follow the person | Running everything as the bot account |
| Results expire without Wrike when gnoto's systemd timer is installed, and `gnoto remove <uid>...` deletes them on demand, for several runs in one command (Daniel, 2026-11-09) | Results shouldn't depend on Wrike to expire | Expiry only through Wrike |
| The Wrike folder's name includes `gnoto`: "gnoto Jobs" | Identifiable in a shared account | "Dashboards" |
| MIT, with the Alkek Center for Metagenomics and Microbiome Research as copyright holder | Matches ampliseq, taxprofiler and nf-core | Naming Daniel or Baylor as well |
| gnoto's outputs are checked and validated from scratch, with no baseline from the old code | The old code's outputs aren't the reference | Recording `cmmr/nextflow` outputs on the fixtures before teardown |
| 13 public datasets are the test fixtures, one for each pipeline path, listed in [fixtures.md](fixtures.md) | Every path is tested on data anyone can fetch, mostly mock communities with known composition | Testing only on CMMR's own data, and the old `test-fastq` sets |
| Slurm and Apptainer first, with scheduler and container calls kept in one place each so others can be added later | Wide support is wanted, but not yet | Supporting SingularityCE or other schedulers from the start |
| No run-time check for images left without a digest. Nextflow's trace records the image each task used, which is enough | Beyond what gnoto aims to control | Failing a run when its trace shows an image pulled by tag |
| `gnoto wrike [task_id]` starts waiting Wrike tasks. For new tasks, the SQS listener only calls it. In both modes, a user timer runs it every `wrike.poll_minutes` (0 turns it off) as a reconciliation scan, which also runs `remove` for runs whose task is gone, copies Expiration dates and reactivates a suspended webhook. Otherwise a person runs it | The form route works without AWS, and SQS mode alone can lose tasks to batched events, a suspended webhook or queue retention | The listener handling tasks itself, which made SQS a requirement. Dropping SQS once polling ran in both modes: Daniel kept it on 2026-11-05 for its speed |
| How ampliseq joins read pairs is a `job.yaml` option, `ampliseq.mergepairs_strategy`, defaulting to ampliseq's `merge` | V3–V5 pairs barely overlap, and the choice changes results, so the user makes it per run | Concatenating automatically whenever V3–V5 is detected |
| `gnoto extend <uid> <YYYY-MM-DD\|never>` keeps a run's results longer, writing the expiry file and, with Wrike, the task's Expiration date. `never` makes a run Unlimited. Removal times count from completion and are never earlier than completion plus `expiration_notice_days`, a floor `extend` and the daily check both enforce | Cleaner than editing files by hand | Editing `retention` in a copy of `job.yaml` kept in `history/<uid>/` |
| Removal times always live in one file per run, `<data_dir>/expiry/<uid>`, for every run that keeps results anywhere, its own run directory included. With Wrike, the task's Expiration date mirrors the file and wins: the listener rewrites the file when a `TaskCustomFieldChanged` webhook reports an edit, the poll scan makes the same update, and the daily check copies every date first. Deleting a task runs `remove` | The daily check reads only runs still waiting to expire, and one store means a deleted or moved task, or Wrike added or removed later, can't leave results that never expire | Keeping the time only in the Wrike task when Wrike is configured. Reading every run's state or history each day |
| `gnoto config s3` and `gnoto config sqs` are separate, each its own CloudFormation stack, attaching its policy to one shared IAM user | A site may want one without the other | One AWS stack set up as a whole |
| A site can set up its own bucket, CloudFront and queue, fill in `s3_bucket`, `results_base_url`, `sqs_queue_url` and `webhook_url`, and `config` only checks them. `service/aws/` ships the CloudFront function, the Lambda and the IAM policies for that case. `config s3 --deploy` and `config sqs --deploy` build the stacks instead, write their outputs to `generated.yaml`, and print the IAM user's new key once | Most sites are expected to set up S3 and CloudFront themselves, and machine-made values stay out of `config.yaml` | Deploying whenever a setting is empty. A default results address of `https://<s3_bucket>` |
| When Wrike is configured but unreachable, `run` and `start` refuse the job | Every job gets its Wrike task | Warning and running the job without a task |
| A copied `job.yaml` measures primers again on its new samples, while an exact re-run from `record.yaml` reuses the recorded ones | New samples should be measured | Reusing the original run's primers, as the old rerun did |
| Each release's entry in `CHANGELOG.md` names the pipelines whose core tables changed, and `gnoto upgrade` shows it. `gnoto selftest` only runs the fixtures and reports, changing nothing. Plain `selftest` checks an install against the current release, and only `selftest --dev` compares a candidate with the last release | Users see whether an upgrade changes their results before it happens | Having `gnoto selftest` write notes or checksums |
| `job.yaml` has a section per pipeline, such as `ampliseq:`. Any parameter that pipeline's schema accepts can be added there and is passed through | Users can reach every upstream option without gnoto adding each one | A flat `job.yaml` limited to the options gnoto offers |
| Hand-added parameters that name a file must use `db:` names, and nf-core's generic and institutional parameters are refused | Keeps site paths out of the record and stops config loading at run time | Passing any schema-valid parameter through unchecked |
| `gnoto prune` removes cached versions and images that no running or waiting job uses, keeping the current release's | The caches only grow, and anything removed is fetched again when needed | Letting the caches grow, and deleting them by hand |
| A failed or cancelled run keeps only its logs, state and task scripts for `core.keep_run_days`. `gnoto run --debug` or `gnoto start --debug` keeps the whole run directory that long, whatever the outcome. A run that fails after Compute has finished keeps its results like a success, and `gnoto publish <uid>` retries Present and Publish | Enough to debug a failure, without holding hundreds of GB. A failed publish shouldn't discard finished results | Keeping every failed run directory whole, or deleting it at once |
| The deliverables zip, which holds the reads (zero or more sets of raw, decontaminated and cleaned FASTQs) and every result, the dashboard's HTML files included, is kept in exactly one place: Globus if it's set, otherwise S3, otherwise `<data_dir>/runs/<uid>/`. With both set, a zip of `globus.min_zip_mb` (100 MB) or less goes to S3 beside the dashboard, and only a larger one to Globus (Daniel, 2026-11-12) | One copy to store, expire and remove, and no site loses its reads for lack of Globus. Most amplicon runs' zips are well under 100 MB, so Globus's rules, of which one user can see at most 100, are kept for the large transfers it's for | Requiring Globus, as the old code did, or copying the zip to every destination |
| Each run on Globus gets a permission of its own: Publish grants anonymous read on `<run_prefix>/<uid>/` alone, and the teardown deletes it. Nothing grants access to the run folder itself, and `lint` fails on a rule that would. The job makes the grant with the client credentials, through gnoto's client, which holds the Access Manager role on the guest collection (Daniel, 2026-11-12) | Daniel's test showed that one anonymous read rule on the run folder let any signed-in Globus user list every run and download any of them | One rule on the run folder, as first designed, which is what `cmmr/nextflow` used. Rules for the requester's own Globus identity, which every recipient would need an account for. Accepting that results can be found |
| Every database is versioned by its path, such as `db:pplace/v1/bac16s.newick`, and a path never changes content: a new build or upstream release gets a new path. `lock.yaml` keys each entry by its versioned `db:` name, such as `db:pplace/v1` | Older versions can still re-run, and a rebuild can't overwrite files a running job reads | Unversioned names such as `pplace/bac16s.newick` and `16s` |
| Pin the most recent stable release of everything gnoto chooses a version of: Nextflow, the nf-core pipelines, tool and base images, nixpkgs and test images. An older version needs a stated reason. On 2026-11-05 that's Nextflow 26.10.5, ampliseq 3.1.0 and taxprofiler 2.0.1 | Releases are what upstream tests and supports | Carrying over the old repo's pins, such as ampliseq's unreleased `827a6b7` and a Nextflow floor of 25.10.4 |
| `gnoto-rbiom` is built with Docker from `rocker/r-ver` by digest, and pak installs a lockfile resolved against Posit's CRAN snapshot of one date. rbiom comes from its GitHub commit until a release with the fixes is on CRAN or conda-forge, and then from a later snapshot (Daniel, 2026-11-07) | Every recursive dependency is pinned by the date, the binaries build in a minute, and rbiom's own fixes arrive without patching | Nix, which needed rbiom and ecodive overridden past the pinned nixpkgs, and patched rbiom 3.1.0 for single-sample runs |
| Until phase 5 publishes them, `lock.yaml` may name an image gnoto builds, such as `gnoto-rbiom`, as a bare `.sif` in `<data_dir>/images/`, the way `IMAGE` names the gnoto image (Daniel, 2026-11-06). Phase 5 published them, and a bare `.sif` now serves only to test an unpublished recipe in the test bed: CI's check refuses one | Nothing outward-facing has to happen before the images are stable | Pushing `gnoto-rbiom` to GHCR in phase 3 |
| Without Slurm, `run` and `start` return at once, as they do with Slurm: the launcher starts the job on the host, detached, once the image has exited, and only ever runs a gnoto job that way (Daniel, 2026-11-06) | A process started inside the image would lose the image and the helper with the command that started it | Running the job in the foreground of `run` |
| `lint` offers to fetch missing databases from phase 3 on, and the pplace and 16S builders, which ampliseq's defaults need, came forward from phase 5, at versioned paths (`pplace/v1`, `16s/v1`). Phase 5 keeps the lock file's digests and `lint --deep` (Daniel, 2026-11-06) | A job on fresh storage can then run from `gnoto lint --yes` alone | Reporting missing databases only, and copying the old built references by hand |
| The pages' CSS is built once with the latest Tailwind standalone CLI, and the fonts (Inter, JetBrains Mono, and only the Material Symbols the pages use) ship in `present/` (Daniel, 2026-11-06) | Pages load nothing from the network, so local results display offline | Tailwind's Play CDN script and Google Fonts, as the old pages loaded |
| ampliseq's report abstract names no site (Daniel, 2026-11-06) | Any site runs the same commit, and the abstract is part of it | A site-name setting |
| Until the version cache, a job may name only the commit its install runs, and `new` pins that. An install that's neither a clean git checkout nor a release runs as `dev` (Daniel, 2026-11-06). Phase 4's version cache replaced this: a job names any version, and only `--dev` runs the install's own files | Phase 4 brings other versions | Accepting any version and running the install's code anyway |
| Phase 3's end-to-end runs are ampliseq on `16s-v4`, in the test bed and on the cluster. taxprofiler and biobakery run end to end only on the cluster, against the old databases (Daniel, 2026-11-06) | Their databases come to hundreds of GB | Building shotgun databases in the test bed |
| `gnoto run [--debug] [--yes] job.yaml` runs a job file, as `gnoto start job.yaml` did. `gnoto new <pipeline>[@<version>]` prints the job file to stdout, with its messages on stderr, and takes any of the file's keys as `--<key>=<value>`: gnoto's options at the top, and `--<pipeline>.<key>` for the section's options and any parameter in the schema. Each value is written with its type, from the option's `values` or the parameter's schema, a `multiple: true` option takes its values comma-separated, and a relative `--samplesheet` is made absolute against the current directory. A key that's neither an option nor a parameter, or a value an option doesn't offer or a parameter's type doesn't fit, is refused, with what's allowed. `gnoto start <pipeline>[@<version>] [--debug] [--yes] [--<key>=<value> ...]` is `new` and `run` in one step, through a temporary job file. `gnoto config <section>` takes settings as `--<key>=<value>`, and then asks nothing. A section `config.yaml` lacks is added on, unless `--off` is given, `enabled` is set only by `--on` and `--off`, and `core` takes settings but not `--on` or `--off` (Daniel, 2026-11-07) | Jobs and settings can be scripted, with no YAML to edit with `sed`, and a job file can go anywhere | `gnoto new` writing `<pipeline>.yaml` in the current directory and refusing to overwrite it. `start` taking a job file. A samplesheet kept as typed, relative to wherever the file is saved. `--enabled=` as well as `--on` and `--off` |
| Every command takes arguments as GNU tools do: `--<key>=<value>` or `--<key> <value>`, with the `=` form in the docs and examples. A command's own flags, such as `--debug`, `--yes`, `--on` and `--off`, take no value, and every other key takes one, so a boolean is written `--x=true`. After a space, a value can't start with `--`, and a key given twice is refused. `lib/args.sh` parses them for the commands in the image, and the launcher follows the same rules for `gnoto init` (Daniel, 2026-11-07) | One rule for every command, and the `=` form reads unambiguously with empty values and values that hold spaces | Only one of the two forms. Valueless booleans for options, such as `--picrust` |
| The old `conf/` directory moved into `pipelines/`: each pipeline's `resources.config` to `pipelines/<name>/`, and `databases.yaml` and `references.yaml` to `pipelines/`. Nothing else at the top of an install starts with a lowercase `c` (Daniel, 2026-11-08) | `config.yaml` tab-completes from `c`, and a pipeline's resource requests sit with the rest of its definition | Renaming `conf/` to another top-level name |
| Until the first release, `<data_dir>/current` names a commit of `main`. An install's first command records one: a tarball's `VERSION`, or a git clone's `HEAD`, which must be on its repository. After that only `gnoto upgrade` moves it. With no version, `upgrade` goes to the newest `v*` tag, and while there's none, to `main`'s tip. Given one, it takes anything a job can name. It shows `CHANGELOG.md` between the two versions, or, until there is one, the commit subjects between them (Daniel, 2026-11-08) | Releases don't exist yet, and `main` is what's tested | Refusing to run until the first release. Following the install directory's `HEAD` on every command |
| A git clone install works like a tarball install: only its launcher and `config.yaml` are used, so `git pull` changes nothing that runs, and `gnoto upgrade` replaces it. The clone's other files run only for the first command, to fetch `current`, or again if its copy has gone, and under `--dev`. `--dev` (`new`, `lint`, `run`, `start`, and `gnoto exec --dev`) runs the install directory's working tree as it stands: its record says `dev: true` with no commit, and `run record.yaml` and `resume` refuse it (Daniel, 2026-11-08) | One way to run for every install, and the cluster keeps its clone | A clone running its own working tree, as phases 1 to 3 did |
| The images gnoto builds, `gnoto`, `gnoto-rbiom` and `gnoto-kneaddata`, and a mirror of Wave's `bowtie2_htslib_samtools_pigz`, are published as public images under `ghcr.io/cmmr/` by GitHub Actions, whenever a push to `main` changes a recipe. Daniel's approval of a push covers the publishing it sets off. The workflow went to `main` on its own, ahead of the rest of phase 5, so that the images existed before a commit named their digests (Daniel, 2026-11-08) | Every push is already his decision, and an image has to be published before a commit can pin its digest | Approving each publish separately. Pushing images from a developer's machine |
| The shotgun databases are fetched fresh on the cluster with gnoto's own fetchers in phase 5, and the lock files' digests come from those fetches. The old `db/` stays until phase 6 (Daniel, 2026-11-08) | A lock's digests have to describe what gnoto's fetchers make, or a fresh fetch at another site fails its check. It's also the fetchers' first real run | Digesting the old databases where they're linked in, and leaving the fetchers' first run to the rollout |
| Phase 1's two determinism probes run on gnoto, not on the old code: the first is the stable-files test, each fixture job run twice and then at another `slurm.max_cpus`, and the second is a build of the human host reference at another CPU count, compared with the lock's tree digest (Daniel, 2026-11-09) | gnoto now pins every tool the test needs, the old code runs other versions, and its outputs aren't the reference. PhiX had already built identically at 6 CPUs in the test bed and 2 on the cluster | Running both on `cmmr/nextflow`, as phase 1 planned |
| Nonpareil keeps its k-mer mode in both shotgun pipelines, though it takes no seed, and its six columns in `alpha_diversity.tsv` are left out of that table's checksum and comparison with `stable-files`' `drop`. `nonpareil_seed` is still passed, for a job that turns on alignment mode (Daniel, 2026-11-09) | k-mer mode is fast, and its estimates vary by about 1% from run to run, which the rest of the table shouldn't be hidden behind | Alignment mode with the seed and a CPU count marked `// fixed`, which repeats exactly but took 61 seconds against a few for 100,000 short reads. Leaving `alpha_diversity.tsv` out of the core tables whole |
| ampliseq's Barrnap keeps ampliseq's `--reject 0.1` for paired reads that merge, `sequencing_type` `illumina_pe` with `mergepairs_strategy` `merge`, almost every run, and takes `--reject 0.05` for any other, so an ASV aligning 5% of the gene counts. The SSU filter stays on for every run. Both parameters are in the record, so an exact re-run takes the same cutoff (Daniel, 2026-11-10) | A single-end run's ASVs of about 150 bp align 9% of 16S, so at 10% none counted, and ampliseq stops a run whose SSU filter would leave nothing. At 5%, 12 of the `16s-single` fixture's 13 ASVs count | 5% for every run. Turning the SSU filter off for single-end Illumina runs |
| KneadData runs from `gnoto-kneaddata`, an image gnoto builds: KneadData 0.12.4's BioContainers image by digest, with the `kneaddata` package from KneadData's `master` at commit `353d1ca`, and always at least 2 threads. The modules go back to a BioContainers image once a release has the fix (Daniel, 2026-11-10) | 0.12.4's parallel TRF fails a sample whose reads, split across `--threads` processes, end just as one process's share is closed: 49 read counts of 1 to 240 at 16 CPUs, such as a blank with 4 reads left, or 98 orphans beside 3,000 pairs. One sample's deterministic failure stops the run. `master`, 8 commits past 0.12.4, has upstream's fix, and no release does. With 1 thread, KneadData writes its own progress into the start of TRF's results, in 0.12.4 and `master` alike, so each file's first repeat read is kept | A `kneaddata_trf_parallel` in `workflows/biobakery/bin` that gives a small input one process, which `cmmr/nextflow` uses. Installing `master` with pip, which fetches setuptools and Trimmomatic's adapters unpinned. 0.12.4 with 1 thread for a small sample: the counts that matter are each file's after trimming, which only KneadData sees, and 1 thread keeps a repeat read |
| ampliseq's `DADA2_TAXONOMY` runs in `gnoto-dada2`, an image gnoto builds: the image ampliseq's DADA2 modules name, by digest, with DADA2 rebuilt from `cmmr/dada2`, a fork of DADA2's repository, at a commit on `RELEASE_3_22-seeded-tie-breaks`, Bioconductor's 1.38.0 with one change that seeds the classifier's tie-breaking from R's generator. ampliseq's `lock.yaml` names it under `process_images`. The change is offered upstream as benjjneb/dada2 pull request 2230, and the process goes back to ampliseq's image once a DADA2 release it runs has the fix (Daniel, 2026-11-11) | 1.38.0's `assignTaxonomy` breaks an exact tie between two reference taxa with a generator seeded from `std::random_device`, which `set.seed()` doesn't reach. In its image, a query tied between two species, classified 24 times after `set.seed(100)` in three R sessions, got confidences from 39 to 59 and named either species or none, and the fourth selftest named a species in `v5v6` that the reference hadn't. DADA2's own issues 1115 (2020) and 2211 (2026) report it, unfixed | Comparing the taxa as they are, so that a re-run or selftest reports such a difference now and then. Leaving the species level out of the comparison. Fixing the bootstrap draws' overlap between sequences that issue 2211 also reports, which would change every confidence, not only ties |
| A paired sample KneadData leaves with no pairs, only orphans, is dropped from the run, as a sample with no reads is (Daniel, 2026-11-10) | KneadData then lists its orphans as single-end reads, only mate 2's when both mates have some, which EsViritu, given only a paired sample's mates, can't run on, and that stops the run. A paired library with no pair left is a failed library or an empty blank | Keeping its orphans, with KNEADDATA naming them as orphans and EsViritu profiling them as unpaired reads |
| An ampliseq job whose `mergepairs_strategy` is `concatenate` or `consensus` skips DADA2's exact species match, `skip_dada_addspecies`, so it has no `Species_exact`; the classifier's `Species` stays (Daniel, 2026-11-10) | Both join a pair that doesn't overlap with 10 Ns, and `addSpecies` stops the run at any base that isn't ACGT. `consensus` is chosen when some pairs don't overlap, so it fails as often as `concatenate` | Skipping it for `concatenate` alone |
| A value whose last digits vary from run to run is read past them for the comparison: ampliseq leaves out Faith's PD, which EPA-NG's placements decide, and HUMAnN's tables are read at 12 significant digits. DADA2's bootstrap confidences, left out at first, are compared again now that `gnoto-dada2` breaks their ties the same way every run (Daniel, 2026-11-12). The rest of each table stays compared byte for byte (Daniel, 2026-11-10) | On the cluster, two runs of one job at one CPU count gave Faith's PD 0.6% apart, confidences one replicate apart and a HUMAnN sum 3e-15 apart, while the test bed gave the same classifier output at 4 threads and 1. The cluster's nodes are all one CPU model, and two runs of HUMAnN on one node differed (2026-11-11), so it's the tools, not the hardware, that don't repeat to the last digit. The confidences were DADA2's unseeded tie-break, and with `gnoto-dada2` the fifth and sixth selftests gave identical taxonomy tables, confidences included | Comparing them as they are, so that a re-run or selftest landing on other nodes reports small differences |
| taxprofiler's selftest runs `wgs-phix` in a job of its own, `phix`, beside the mock, and a follow-up lets taxprofiler drop a sample with no reads MetaPhlAn can use, as the next row says (Daniel, 2026-11-10) | MetaPhlAn stopped the whole run on a sample with no read over 70 bp, as a nearly empty blank is after PhiX removal, and taxprofiler has no way to drop one. The `mixed` job can then repeat and get reference tables | Fixing it within phase 6. Taking `wgs-phix` out of taxprofiler's selftest |

The Overview names it as dropped. A file Nextflow can't read as gzip is left to the tool (Daniel, 2026-11-10) | Kraken2 writes such a sample an empty report, and taxpasta's Kraken2 merge, which has to pass, fails on it for every sample, so no `errorStrategy` can save the run. Nextflow reads only the start of each file, in its own process | An `errorStrategy` for each failure, which can't reach taxpasta. Refusing an empty sample before the run, which can't see what fastp and host removal leave |

Compared, they still show a change in HUMAnN's results between versions | Leaving them out of `stable-files`, so that nothing would notice such a change |

| With S3, a running job's progress page is published at its results address, `index.html` and `progress.json` uploaded whenever they change, at most every 10 seconds, and the Wrike task gets a "Results" link field at submission, which the dashboard later replaces at the same address (Daniel, 2026-11-12) | A requester can follow the run from the link on the task from the start, as with the old code | Publishing only once the run completes |
| The floor is phase 4's commit until the first release, then that release. Each commit carries a one-line `COMPAT` file, `1` from phase 4, and gnoto runs only commits whose `COMPAT` is at least its own. ## Recommendations accepted without objection

| Decision | Why | Set aside |
| --- | --- | --- |
| A job names a commit, and that commit pins everything else | One thing to record, one thing to fetch | A `.sif` or `.nix` file as a job's identity |
| Site config says where a job runs and where results go, never what the results are. An unset value can skip side effects, but never results | This is the core reproducibility rule | Skipping result-making steps when a setting is unset |
| One repo for all pipelines, with one version number | About 9,600 lines are shared by every pipeline, against about 12,300 specific to one (by `wc -l` on 2026-11-05), and separate repos would need a third for the shared code | Separate `gnoto-ampliseq` and `gnoto-taxprofiler` repos. Per-pipeline tags in this repo remain possible later |
| Tool containers stay per-process, pinned by digest | nf-core pipelines expect them, and upstream tests those builds | One large image, or rebuilding every tool with Nix |
| Images are pushed as OCI from CI, not as `.sif` files | Docker and Podman users can run them, and identity is the registry digest | `oras://` SIF, a `.sif` on the `rbiom` repo |
| The `gnoto-rbiom` recipe stays in this repo | A recipe change lands in the same commit as the script using it | Keeping it in the `rbiom` repo |
| The job runs in three stages: compute, present, publish | Someone with no cloud account still gets results and a dashboard | Keeping science inside the upload scripts |
| Fetch code with git into a cache whose files are read-only and whose directories stay group-writable | Git verifies content against the commit | Temporary directories, downloaded archives |
| A command reaches another version through a hand-over: the current version resolves and fetches it, and once the image exits, the launcher runs that version's launcher with the same arguments, `GNOTO_INSTALL_DIR` and `GNOTO_RESOLVED`. `repo.git` fetches each commit's whole history. `prune` keeps any version used in the last hour, and every local `.sif` until phase 5. The test bed fetches from a repository of its own, holding test commits that go nowhere else (2026-11-08) | A version's code runs in its own image, and the install's launcher has no git. gnoto's history is a few megabytes, and with it `upgrade` lists the commits between versions and `lint` can tell whether a release or `main` reaches a commit. A local `.sif` can't be pulled again | Running another version's code in the current version's image. Fetching with `--depth 1`, as first designed |
| Step containers run with `--cleanenv --no-home`, `LC_ALL=C.UTF-8` and `TZ=UTC`, and the helper submits `sbatch` with a fixed environment | A user's locale, R library paths and dotfiles could otherwise change core tables | Passing the caller's environment and home, which Apptainer does by default |
| Each input's ampliseq batch (`run`) and the sequencing platform are measured values: recorded, and reused on an exact re-run | The batch came from file paths, which differ on a re-run, and it changes DADA2's error model | Deriving them again from the re-run's paths |
| gnoto passes `custom_config_base` empty, and never lets ampliseq download a reference: each reference choice maps to a `pipelines/databases.yaml` entry, fetched, md5-checked and passed through `*_ref_tax_custom` | ampliseq otherwise loads config from nf-core/configs' `master` branch, and downloads references unchecked at run time, some over `http://` | Passing `*_ref_taxonomy` through, as the old code did |
| The launcher reads `core.data_dir`, `core.db_dir`, `apptainer.bin_dir`, `apptainer.binds`, `slurm.bin_dir` and `slurm.conf` with its own awk, which accepts only `key: "value"` lines under their section, and `lint` checks that `yq` agrees | It needs them before it can start the image that holds `yq` | A second settings file, or starting the image once just to read the config |
| `lint` fails if `$NXF_HOME/config` exists, and warns on any setting in `core.nextflow_config` that could change results, checked on the resolved config. Nextflow is launched from the run directory | Nextflow loads `$NXF_HOME/config`, which sits in the group-writable data directory, into every run, and the earlier check covered only `params` and `container` | Warning only on `params` and `container` |
| `core.nextflow_config` stays. `record.yaml` holds only a SHA-256 of its contents, `run_state.json` holds the full text, and a re-run never applies the recorded one | Its contents can hold site paths, which the record leaves out, and another site's config wouldn't fit | Replacing it with explicit `core.slurm_options` and `core.queue_size` settings. Copying its contents into the record |
| The group on `config.yaml`, or on the install directory before there is one, is gnoto's group. `gnoto init` and `gnoto config` write `config.yaml` in the user's own group, and a shared install is a `chgrp -R` away. Every file and directory gnoto makes, in the install directory, `core.data_dir` and `core.db_dir`, carries that group and is group-readable and group-writable. `config.yaml` and `generated.yaml` are 660. Files in `versions/` are the one exception, and stay read-only | Any group member can run, cancel, extend, remove and prune any job | A separate `core.group` setting; `config.yaml` at 600 or 640 |
| `generated.yaml` takes `config.yaml`'s mode and group, and `lint` checks both | At 600, group members couldn't read the Wrike IDs or `RUN_ID_SALT` that their commands need | `generated.yaml` always at 600 |
| `remove` on a running or waiting job writes the cancel file and a `remove` marker, and the job's followup does the teardown once the job has ended. Every job checks for a cancel file before it starts work | Deleting the run directory at once would delete the cancel file, and the job could then publish removed results | `remove` cancelling and deleting in one step |
| A rejected form task is set to `Failed` with the reason in a comment. In the form route, missing databases are fetched without asking, and the job depends on those fetches with `afterok` | A rejected task would otherwise stay waiting and be linted again every poll, and nobody answers a prompt in the form route | Leaving rejected tasks as `Submitted`, or failing requests that need a new database |
| Form requests may read FASTQs only under `core.input_roots`, checked on each file's real path. Titles, sample names and uids each match one fixed pattern, and `present/` HTML-escapes every value | Form jobs run as the service account and publish their inputs, so a requester could otherwise publish files they can't read. Unescaped values allow script injection on the shared results domain | A readability check only, as the old code had |
| gnoto's own options sit at the top level of `job.yaml`, and upstream parameters in the pipeline's section. `pipeline.sh` declares the keys gnoto owns, which `lint` refuses. A job's section overrides `pipeline.sh` defaults, and `record.yaml` stores the merged set, which an exact re-run passes as recorded | Options such as delivered reads aren't upstream parameters, and a re-run must compute exactly what the first run did | Re-evaluating `pipeline.sh` on a re-run |
| The head job is submitted with `--no-requeue`, `--signal=B:TERM@300` and a time limit from `slurm.job_time`, which `lint` checks against the partition. The followup cancels any task the trace still shows as running | Slurm's default requeue restarts a job on top of itself after a node failure, and a hard kill can leave tasks running | A hard-coded 60-hour limit with Slurm's defaults, as the old code had |
| A database fetch writes into `<name>.tmp.<jobid>` under a lock and renames on success. A marker names the fetch job, so `lint` reports it and `run` depends on it with `afterok` and `--kill-on-invalid-dep=yes` | Two jobs needing the same missing database would otherwise fetch into one path, or a job could start before its database exists. Without the kill, a failed fetch leaves the job queued for good | Fetching in place |
| Every per-run command takes that run's lock, and `prune` takes the cache lock exclusively while `run` holds it shared until its state names its commit. A write that can't get its lock fails, and `lint` checks that `flock` works on `core.data_dir` from login and compute nodes | Races between `extend` and expiry, or `prune` and `start`, would otherwise lose an extension or a version in use | Falling back to unlocked writes, as the old `run_state.sh` did |
| Only the current release checks `config.yaml` for unknown keys. Every version ignores keys it doesn't know, treats a missing key as its default, and skips any Wrike side effect whose field `generated.yaml` lacks | Exact re-runs of older versions, and newer commits run by older installs, would otherwise fail `lint` | Every version flagging keys it doesn't know |
| The Wrike integration needs a Business plan or above. If the bot isn't an admin, an admin creates the workflow and `config wrike` adopts it by name. `lint` checks that the bot's license can create tasks | Only admins on Business plans and above can create custom workflows, and Collaborator, Contributor and Viewer licenses can't create tasks | Checking only for a Collaborator license, which Wrike is discontinuing |
| Once a job is submitted, Wrike updates are side effects: retried with backoff on 429 and 5xx, logged for the daily timer to replay if they still fail, and never allowed to fail a stage or skip cleanup. The network-failure rule in `CLAUDE.md` covers only downloads and pulls a step depends on | A Wrike outage at the end of a run left the old code's tasks `Running` forever, outside expiry | Failing the run on any network error |
| Selftest jobs carry `selftest: true`, skip Wrike, Publish and expiry, and are removed after the report. `selftest` submits and returns, and a followup writes the report that `status` shows. It offers database fetches with sizes per pipeline. `--dev` reads the last release's `selftest.yaml` from its tag | Hours of jobs can't wait in the foreground on a login node, and test runs shouldn't create Wrike tasks or publish | Running selftest in the foreground, as ordinary jobs |
| No hardware detection. A re-run or selftest reports "identical" when checksums match, and otherwise runs one generic comparison over each core table's numeric cells, reporting the largest relative difference | Nothing records the hardware, and one comparison is less to build than one per table type | Detecting a hardware class. A comparison step for each table type |
| `images/` holds only shared `.sif` files, each pulled to a temporary name and renamed. `APPTAINER_CACHEDIR` points at a per-user directory on node-local storage | Apptainer's layer cache can't be shared between users, and by default it fills home directories | One shared Apptainer cache |
| `containers.config` is built by scanning every module for its Docker-style address and pinning each to an OCI digest, ignoring the `https://` image files nf-core names for Singularity and Apptainer. `pipelines/lock.sh` writes a `withName` selector for each process name and each alias it's included under, and an address with no registry takes the pipeline's `apptainer.registry`. Testing changed one part (2026-11-08): Seqera's pixi-built images put their tools on `PATH` only in their entrypoint, which `apptainer exec` never runs, so a process whose image is one of those takes the module's own `https://` file for Apptainer, which Seqera's registry serves at a path naming its SHA-256, and `lock.sh` checks the file against it | An `https://` file generally has no registry digest, and `nextflow inspect` covers only the processes one set of parameters turns on. A selector beats the module's own `container`, so no upstream code changes. In ampliseq's first run by digest, `DUCKDB_TABLE2PARQUET` exited 127, `duckdb: command not found` | Generating it with `nextflow inspect`. The `oras://` builds ampliseq lists, which cover only its nf-core modules, not its own `FORMAT_TAXONOMY`. Setting `PATH` for those processes by hand |
| `status` checks each running job against `squeue` or `sacct` by job ID, and shows "Lost" when Slurm has nothing running. The listener and timers write heartbeat files that `status` reads | A job killed with its followup never updates its state, and one user can't query another account's systemd units | Trusting the state files alone |
| A Slurm job that failed on a node without creating its log is reported as dying at launch there, naming the node, for a Nextflow task, a head job or a followup. Three checks ask whether each node the partition is starting jobs on can see and write `core.data_dir`, see `core.db_dir`, use `flock` there, and has `slurm.min_tmp`, 50 GB by default, free in `/tmp`: `start` over `ssh`, and not at all where `ssh` reaches no node; `lint` over `ssh`, or else with a small Slurm job pinned to each node with CPUs free now; and `gnoto config slurm --probe`, with a job pinned to every node, waiting up to an hour for busy ones. Where ssh reaches some nodes, a node it can't reach fails the check too (Daniel, 2026-11-09). A node that fails a check, or that a job died at launch on, goes on `<data_dir>/excluded-nodes`, and every job gnoto submits, Nextflow's tasks included, gets `--exclude` with the listed nodes. A check takes a node off once it passes | A node missing a mount fails each job Slurm puts there before its script runs, and Nextflow reports only "terminated by the external system". On the cluster, one such node failed taxprofiler's two largest tasks. Other jobs can fill a node's `/tmp`, where tools inside a task write. `ssh` reaches a busy node at once, so the check before each job costs seconds, and `lint` never waits on a busy queue, while the probe covers the busy nodes `lint` can't. A user usually can't drain a node, so gnoto steers its jobs around one. `slurm.min_tmp` is a setting so a site whose nodes have a small `/tmp` can lower or clear it | Checking one node with one job, Slurm jobs to every node from `lint`, which wait on busy ones, and passing on Nextflow's message alone. An allow list of good nodes, since `--nodelist` alone asks for every node it names, and the list would leave out new nodes and ones not checked. `slurm.exclude` in `config.yaml`, which other users can't write. A fixed 50 GB for `/tmp`, which would leave no node on a cluster with a smaller one. A Slurm job before each job where `ssh` isn't available, which would wait on a busy queue |
| `gnoto resume [uid]` resumes a failed or cancelled run through Nextflow's `-resume`, in its own run directory and at its own commit, and is built in phase 4. A failed or cancelled run keeps `work/` and `.nextflow/` until `core.keep_run_days` after it ended, so it can be resumed | Every task that finished comes from the cache, which saves days on a large run that failed near its end. A resumed run must use the code it started with, which the version cache provides | Building it in phase 3, before a job can run at its own commit. Resuming only `--debug` runs, which few runs would have been started with |
| `status <uid>` shows a run's state, stage, Slurm job IDs, paths, error message and Nextflow's report on the failing task, which holds its command's output and error, or the last 20 lines of `.command.err` when there's no report. `history/<uid>/` keeps `job.yaml` and a short error summary as well, and `prev_run_id` reads from there. `logs/` holds service logs, which the daily timer rotates | After `keep_run_days` a failure's cause would otherwise be gone, and `prev_run_id` would fail once results expire | Keeping only the state and record in `history/` |
| `generated.yaml` records the host the systemd units live on. `config systemd` refuses another host without `--move`, each unit does nothing unless it's on the recorded host, and `status` shows the host | Units and linger belong to one login node, and two sets of timers would race each other's teardowns | Installing units wherever `config` runs |
| `run_state.json` is never published. `progress.json` carries only what the page shows, the published `job.yaml` has no paths, and the pages load no third-party scripts or fonts | Public pages would otherwise leak hostnames, paths and the Wrike task ID, and run a third-party script | Publishing `run_state.json`, and loading Tailwind and fonts from CDNs, as the old code did |
| Release checks run in CI on `main` before anyone tags. The tag's job creates a draft release, uploads the tarball and its `.sha256`, then publishes it. Phase 8 lists the release as numbered steps | A check that runs only on the tag fires after the tag is public, and a failed upload would otherwise leave a release without its tarball | Running the release checks on the tag |
| `record.yaml` holds each input's size as well as its SHA-256. A re-run shortlists files under `--inputs` by size, and the job checks each SHA-256 while staging | Hashing a large input folder on the login node would make `start` slow | Hashing every candidate file in `start` |
| `status` runs no integration checks itself. The daily timer runs `lint` and writes a health file beside the heartbeats, and `status` shows it with its age | One set of checks, a fast `status`, and the same answer for every user | `status` repeating every check on each call |
| Every Globus call uses the client credentials in `config.yaml`, and nothing runs `globus login` | A `globus login` token lives in one person's home directory, which other group members can't use | `globus login` during `config` |
| `record.yaml` is the job file resolved: the same keys, plus `schema`, the resolved `repository` and `commit`, a pipeline section holding every parameter passed, `outputs`, and last of all `inputs` in place of the samplesheet, because it can be very long. A re-run reads it with the code that reads a job file | One shape and one reader for both files | Separate `answers` and `params` sections |
| An image gnoto builds is tagged on GHCR with the first 12 characters of its recipe's git hash, and a copy with its source's tag. `images/publish.sh` runs skopeo from its own image by digest, learns gnoto's digest from a local registry first, and fails when the tag already holds another digest. `images/mirrors.txt` lists the images gnoto copies, by tag and digest (2026-11-08) | A recipe already published is left alone, and the tag says which recipe built an image. The Nix build and the pinned skopeo give the same digest anywhere, so a changed digest means the build no longer reproduces | Tagging by commit, which would push the same image again for every commit. The runner's own skopeo, whose gzip could change with the runner |
| CI's check, `pipelines/lock.sh check`, runs in the gnoto image `IMAGE` names, on every push and pull request. It fails on an image by tag or a digest its registry doesn't have, anywhere a job's images are named, and on a `containers.config` that no longer matches the modules at its pinned commit (2026-11-08) | The check runs with the tools every other script does, at the version they're pinned to | Relying on the tools GitHub's runner happens to have |
| A database a lock pins must have the lock's file count and bytes, or `lint`, `run`, `start` and the job fail; `lint --deep` and an exact re-run's job also compare its tree digest. A `db:` name no lock pins, such as a site's own database, gets a warning, and the record keeps its file count and bytes, which an exact re-run checks. `record.yaml` gains `databases`, each the lock's entry or the measured size (2026-11-08) | A path never changes content, so a mismatch is the wrong database. Hand-added parameters may name a site's own database, which no commit can pin | Refusing any database a lock doesn't pin. Hashing an unpinned database at every run |
| The shotgun databases come from `steps/fetch_shotgun_db.sh`, the old `fetch_taxprofiler_db.sh` without its sewage reads, which the fixtures replace, and the host references from `steps/build_host_reference.sh`, at `hostremoval/<name>/v1`. An entry's `fetch_job` sets its fetch job's CPUs, memory and time. The md5s HUMAnN's publisher doesn't list are the files as fetched on 2026-11-08 (2026-11-08) | The fetchers serve biobakery as well as taxprofiler. A host reference's path had no version, and a human index needs far more than the default 2 CPUs and 8 GB | Keeping the old name. One size of fetch job for every database |
| A message that tells the user to run a gnoto command names the launcher so it runs as written: `gnoto` when that's what `gnoto` on the user's `PATH` runs, and otherwise the install directory's launcher by its absolute path. The launcher decides on the host and passes it in as `GNOTO_LAUNCHER`. Usage text, a job file's comment and the pages keep the plain `gnoto` (2026-11-09) | The install directory usually isn't on `PATH`, so `Follow it with: gnoto status <uid>` failed as written on the cluster | Always the bare `gnoto`. Always the full path, which is longer than it needs to be where `gnoto` is on `PATH`. Echoing what the user typed, which can be relative, and which only the install directory's launcher sees, since it hands every command on and is never upgraded |
| Cancelling goes through a cancel file | Slurm won't let the service account cancel another user's job, or a user cancel the service account's | `scancel` from the listener |
| Promise identical ingredients everywhere, identical core tables on the same hardware, and equal core tables within a tolerance elsewhere | Byte-identical output across machines isn't realistic | A blanket byte-identical promise |
| A selftest's reference is the core tables themselves, in `pipelines/<name>/selftest/<job>/`, and `selftest.yaml` lists the jobs: each one's samples, as fixture files, and its options. An exact re-run compares its tables with the ones beside its record, which `run` copies into the run directory when their checksums are the record's. The report keeps each run's tables for the maintainer to copy in (2026-11-09) | The numeric comparison needs the other run's values, which checksums alone can't give, and a commit that changes a table shows how in its diff. A published record sits in `results/` beside its tables | Checksums alone in `selftest.yaml`, copied by hand, which leaves a selftest at another site nothing to compare its numbers with |
